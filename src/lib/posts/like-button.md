## いいねボタン付けたい！

ブログにいいねボタン付けたい！それは突然の衝動でした。 3 日前にはなかった感情。そう、いつだって「あれやりたいこれやりたい」が出てくるのは突然。

でもこの衝動、思ったより長い旅の始まりだったんですよね。作ってから今日までに、**このいいねボタンは 3 回引っ越しています**。

## お手軽にデータを保存したい

「イイネ」のカウントをするだけなので、サーバー側にデータを保存する仕組みを作るのは面倒だなぁ。という僕のワガママは、いつものように AI さんに解決してもらいました。

いろいろ提案してもらって、エッジ（世界中に分散したサーバー）で動く SQLite データベースである [TURSO](https://turso.tech/) というサービスを使うことにしました。

## なぜ TURSO ？

[Supabase](https://supabase.com/) 、 [Firebase](https://firebase.google.com/) 、 [Upstash](https://upstash.com/) 、 [Neon](https://neon.tech/) 、 Cloudflare などが検討候補に上がりましたが、とりあえず簡単に使えて、軽量に扱える。しかも無料で、無料枠の制限が緩い、しかも低遅延。このへんが自分にとっては評価のポイントとなりました。

サーバー代 **0 円** でいいねが数えられる。最高じゃないですか。

## SQL を書きたくない

でも実装して 1 日で、次の不満が出てきました。

[SQL](https://ja.wikipedia.org/wiki/SQL) （データベースを操作するための言語）を TypeScript のコードの中に文字列として書いてたんですが、これ、**文法的なチェックが一切効かない**んですよ。書き間違えても、実際に実行してみるまで分からない。

不具合の発見ポイントが後ろにあると無駄な時間を消費しちゃいます。そういうのはなるべく早めに発見しておくのが、効率化につながるんです。

## ORM を使ってみるぞー

ORM （ Object-Relational Mapping ／ オブジェクト関係マッピング）は、プログラミング言語のオブジェクトとデータベースの表を対応させる仕組みのこと。意味わからんね。

簡単に言うと、**SQL を書かずに、いつものコードでデータベースを操作できるようにする技術**です。

これ使うと、 TypeScript の型チェックが効く、入力補完がサクサク効く、データベースの変更履歴（マイグレーション）も管理しやすい。メリット盛り沢山なんです。

というわけで [Drizzle](https://orm.drizzle.team/) という軽量 ORM を入れて、コードの中から「生の SQL 」を全部追い出しました。軽量なのでパフォーマンスも全く問題なし。

ここまでが 2025 年 11 月の話。 **記事にしたのは 2 日連続**でした。それくらい勢いがあったんですよね。

## あんまりアクセスしたくない

いくら無料枠の上限が緩いと言っても、可能な限りアクセス数は減らしたい。いくら低遅延だと言っても、そのちょっとした待ち時間が気になることもある。

そこでキャッシュ（一時保存）を挟むことにしました。しかも **2 段重ね**で。

| 段     | 場所                                                   | 保持時間  | 役割                               |
| ------ | ------------------------------------------------------ | --------- | ---------------------------------- |
| 1 段目 | サーバーのメモリ                                       | **1 分**  | 同じサーバーへの連続アクセスを弾く |
| 2 段目 | [Cloudflare KV](https://developers.cloudflare.com/kv/) | **30 分** | 世界中のどのサーバーから来ても効く |

いいね数って、 1 分古くても誰も困らないじゃないですか。この「別に困らない」を見つけたら、そこはキャッシュしていい場所です。

データの永続性はデータベースに任せて、速度は自分の側で稼ぐ。いい感じの分業になりました。

## そして、引っ越しが始まる

ここから話が変わります。

2026 年の 1 月 4 日、僕はこのサイトを **Cloudflare に丸ごと引っ越しました**（ [#244](https://github.com/joshuafolkken/joshuafolkken-com/issues/244) ）。そして同じ日のうちに、キャッシュも Cloudflare KV に載せ替えています（ [#253](https://github.com/joshuafolkken/joshuafolkken-com/issues/253) ）。 1 日で 2 回引っ越したことになりますね。働きすぎ。

こうなると、残っているのはデータベースだけなんですよ。

家の中の家具を全部新居に運び終わったのに、**冷蔵庫だけ前の家に置きっぱなし**。そんな状態です。動いてはいる。でも気持ち悪い。

誤解のないように書いておくと、 **TURSO に不満があったわけではまったくない**んです。むしろ好きなサービスです。無料枠は緩いし、速いし、導入も一瞬だった。

理由は単純で、 **Cloudflare で同じことができるなら、 Cloudflare にまとめたかった**。

僕はこれから Cloudflare をどんどん使っていくつもりでいます。だったら、同等のサービスが自分の手で使いものになるのかを、**自分の目で確かめておきたい**じゃないですか。カタログを眺めて「良さそう」と言っているだけでは、いざ本番で使うときに何も分からない。

引っ越し先の街に住むと決めたなら、近所のスーパーがちゃんと使えるか、一度は買い物に行ってみるべきなんですよね。

## Cloudflare D1 へ

というわけで 2026 年 3 月 1 日、データベースを [Cloudflare D1](https://developers.cloudflare.com/d1/) に移しました（ [#333](https://github.com/joshuafolkken/joshuafolkken-com/issues/333) ）。

この引っ越しで何が消えたか、差分を見ると一目瞭然でした。

| 消えたもの     | 中身                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| `.env.example` | **ファイルごと削除**。 `TURSO_DATABASE_URL` と `TURSO_AUTH_TOKEN` の 2 行しか入っていなかった |
| CI の設定      | 4 行。テスト実行時に上の 2 つを渡すための記述                                                 |

つまり、**秘密の値を管理する必要がまるごと無くなった**んです。

D1 は Cloudflare の中で動いているので、接続先も認証トークンもいりません。設定ファイルに「 `DB` という名前でこのデータベースを使う」と 1 行書くだけ。あとは Cloudflare が勝手に繋いでくれます。

トークンって、漏れたら怖いし、期限が切れたら動かなくなるし、新しいパソコンで開発を始めるたびにコピーしてこないといけない。**そういう面倒が丸ごと蒸発しました**。

## で、大変だったんでしょう？

……それが、**びっくりするほどすんなり終わったんです**。

拍子抜けするくらい引っかかりがなかった。なんでだろうと思って、あとから差分を見返して気づきました。 **3 か月前の自分が仕込んでいた**んですよ。

データベースへの接続部分、変わったのは実質ここだけでした。

|                  | 移行前               | 移行後           |
| ---------------- | -------------------- | ---------------- |
| 読み込む部品     | `drizzle-orm/libsql` | `drizzle-orm/d1` |
| 接続コードの行数 | **27 行**            | **10 行**        |

そして **データを読み書きしている部分は、 1 つも書き換えていません**。「この表からこの条件で取ってくる」というコードは、相手が TURSO だろうと D1 だろうと同じまま動きました。

これ、 ORM を挟んでおいたおかげなんです。 ORM がデータベースとの間に通訳として立っていたから、**通訳の相手が替わっても、こちらの喋り方は変えなくてよかった**。

型チェックが効くから入れただけだったのに、 3 か月後にまったく別の場面で効いてくる。 **未来の自分が助かる仕込みって、こういう地味な顔をしてるんだなぁ**と思いました。

## 「イイネ」の状態はどう保存してる？

ちなみに、あなたが「もう押したかどうか」は、ブラウザの Local Storage （ブラウザ自体が持っている小さな保存箱）に入れています。

なので実は、**ブラウザのデータを消したらもう一回押せます**。連打はできない仕様ですが、そこは性善説ということで。（バレたらどうしよう）

## 今の構成

3 回の引っ越しを経て、いまはこうなっています。

| 役割                 | 使っているもの                     |
| -------------------- | ---------------------------------- |
| データの保存         | Cloudflare D1                      |
| データベース操作     | Drizzle ORM                        |
| キャッシュ           | メモリ 1 分 ＋ Cloudflare KV 30 分 |
| 押したかどうかの記録 | ブラウザの Local Storage           |
| 動いている場所       | Cloudflare Workers                 |

最初に書いた記事のタイトルは「サーバー代 0 円 で『いいね機能』を実現する。 TURSO × SvelteKit 最強説」でした。**TURSO はもう使っていません**。でもサーバー代が 0 円 なのは、今も変わっていません。

## 小さい機能ほど、実験台に向いている

振り返ってみると、 **このいいねボタンが小さくて単純だったことが、全部の鍵だった**と思うんです。

やっていることは「数を 1 増やして、読み出す」だけ。壊れても誰も困らない。だからこそ、 Cloudflare KV も D1 も、**このボタンで試してから本番の判断ができました**。いきなり大事な機能で新しいサービスを試していたら、こんなに気楽には引っ越せなかったはずです。

新しいサービスを評価したいとき、**評価用に何かを作る**のではなくて、**すでに動いている一番小さいものを引っ越させてみる**。これが一番てっとり早いし、正直な答えが出ます。カタログには書いていないことが分かりますから。

TURSO とは離れることになってしまったけれど、悪いところがあって別れたわけじゃない。**また機会があれば使いたいサービス**です。

そして相変わらず、この記事の下にもいいねボタンがあります。中身は 3 回引っ越しましたが、やることは何も変わっていません。ポチッとしてくれると、モチベーションが爆上がりします。「イイネ」の練習にご利用ください！
