最近、GitHubのREADMEやライブラリのドキュメントを見ていると、インストールコマンドが3つ並んでいるのをよく見かけませんか？

```bash
pnpm install ...
yarn install ...
npm install ...
```

「どれでもいいよ」と言われているようでいて、なぜか `pnpm` が一番上に書かれていることが多い気がします。「なぜ3つもあるんだ？」「なぜnpmが一番下なんだ？」と疑問に思ったことはありませんか？

これまで私は `npm` 一筋でやってきましたが、この並び順が気になり調べてみたところ、どうやら `pnpm` が今の自分にとってベストな選択肢のようだと気づきました。そこで今回、思い切って `npm` から `pnpm` へ移行することにしました。

## なぜ pnpm なのか？

私が `pnpm` を選んだ主な理由は以下の2点です。

1.  **ディスク容量の節約**: `pnpm` はパッケージを効率的に保存するため、ディスクスペースを大幅に節約できます。
2.  **高速な動作**: インストール速度が非常に速く、開発体験が向上します。

容量も削減できて動作も快適なら、乗り換えない手はありません。

## 移行の道のり

「よし、移行しよう！」と意気込んだものの、実際にはコマンドを置き換えるだけでは済みませんでした。

### コマンドの変更

当然ですが、`npm` コマンドを `pnpm` に置き換える必要があります。特に `npx` コマンドは、基本的にすべて `pnpm exec` に変更しました。

### スクリプトと設定の修正

`package.json` 内の `preinstall` や `postinstall` スクリプトも修正が必要でした。また、CI/CDパイプラインである GitHub Workflows の設定も `pnpm` 用に書き換える必要がありました。

「ほぼコマンドを変えずに移行できたら楽なのに」と思うこともありましたが、それぞれのパッケージマネージャーには制作者の譲れないポリシーや設計思想があるのでしょう。そこは郷に入っては郷に従えです。

### 安全性のための設定

今回の移行に合わせて、新しいパッケージのインストールに関する設定も追加しました。
具体的には、**リリースされてから24時間経過していないパッケージはインストールしない**ように設定しました。

セキュリティリスクを避けるために「1週間待つ」という考え方もありますが、Webの世界は進化が速く、パッケージはどんどん更新されていきます。「1週間も待てないし、3日も待てない！」ということで、バランスを取って24時間に設定しました。

## Bun との比較

実は以前、話題の `Bun` への移行を試みたことがありました。その時は移行自体はできたものの、ビルド周りで不具合が発生し、泣く泣く利用を諦めた経緯があります。

しかし今回の `pnpm` への移行は、細かい修正は必要だったものの、最終的にはビルドも含めて問題なく動作させることができました。

## 最後に

今回の移行で細かい設定ファイルも色々と変更しています。もし具体的な変更内容が気になる方がいれば、ぜひコミットログを覗いてみてください。

この記事が、私と同じように「`pnpm` 気になるけど、どうしようかな？」と迷っている方の背中を押すきっかけになれば嬉しいです。
