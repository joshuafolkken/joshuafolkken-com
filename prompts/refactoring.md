# リファクタリング支援プロンプト

このプロンプトは、AI にリファクタリング提案を行う際の指示書です。小さくて簡単な方法から提案し、ユーザーが考えて対応できるよう配慮します。

**「リファクタリングを提案して」とだけ指示すれば**、以下が自動的に実行されます：

- 選択ファイルがない場合 → 変更ファイルや現在のブランチの変更内容を自動的に確認する
- 変更ファイルやブランチ変更がない場合（main ブランチ等）→ プロジェクト全体を確認する
- 特定したファイルを中心に、関連しているものや似たものがあればそちらもリファクタリング対象に含める

## 重要な動作指示

**「リファクタリングを提案して」と指示された場合、以下の動作を実行してください：**

1. **リファクタリング対象の特定（優先順位に従う）**
   - **選択・開いているファイルがある場合** → そのファイルを中心に分析
   - **選択・開いているファイルがない場合** → 変更ファイル（`git status` の M/A/D 等）を確認し、それを中心に分析
   - **変更ファイルがない場合** → 現在のブランチの変更内容（main 等との差分）を確認し、それを中心に分析
   - **ブランチ変更もない場合**（main ブランチ等）→ プロジェクト全体を分析し、最も改善が必要なファイルを特定

2. **関連・類似ファイルの拡張（網羅的に実施）**
   - 上記で特定したファイルを中心に、**関連しているものや似たものがあればそちらもリファクタリング対象に含める**
   - インポート関係、同じディレクトリ、類似機能、依存関係のあるファイルを確認する
   - **重要**: 1回の提案で漏れを防ぐため、以下の拡張を必ず実施する：
     - 対象ファイルがインポートしているすべてのファイル
     - 対象ファイルをインポートしているすべてのファイル
     - 同じディレクトリ内のすべてのファイル
     - 同じ機能領域（例: sticky-header 関連なら constants, components, utils すべて）のファイル
     - 類似名のファイル（例: Header\* を分析するなら SocialLinks, MenuNav など関連しうるもの）

3. **除外条件の適用**
   - 以下のファイル・フォルダは分析対象から除外する：
     - `demo` フォルダ内のすべてのファイル
     - ファイル名に `demo` が含まれるファイル
     - `src/routes/stories` フォルダ内のすべてのファイル
     - ファイル先頭に `/* @refactor-ignore */` コメントが含まれるファイル

4. **網羅的リファクタリング提案の実行（1回で洗い出す）**
   - **重要**: 提案は1回の分析で可能な限りすべて洗い出す。複数回のやり取りで「新たな提案」が出続けることを避ける。
   - 特定したファイル（および関連・類似ファイル）のリファクタリング案を提案する
   - 提案前に「4.1 クロスファイルパターン検索」を必ず実施し、類似パターンを見逃さない
   - 高・中優先度の候補がある場合 → 該当する候補を**すべて**提案する（件数制限なし）
   - すべて低優先度の場合のみ → 最大3つまで提案する
   - 実装可能なサンプルコードを提供
   - コメント提案は不要

4.1 **クロスファイルパターン検索（必須）**

- 提案を確定する前に、分析対象スコープ全体で以下を検索し、漏れがないか確認する：
  - **同一・類似の文字列リテラル**: 同じ Tailwind クラス、同じマジックナンバー、同じ文言が他ファイルにないか
  - **同一・類似の型定義**: `'desktop' | 'mobile'` など重複している型が他にないか
  - **同一・類似の構造**: 同じ UI パターン（アイコン+テキスト、ボタン+リンクなど）が他にないか
  - **定数化の余地**: ハードコードされた値が、既存の定数ファイルや他ファイルと共通化できないか
- 1つのファイルを改善したときに「似たパターンが別ファイルにもある」と気づくような漏れを、事前に洗い出す

5. **プロンプトの説明は行わない**
   - このプロンプトの内容説明は不要
   - 直接リファクタリング提案に移る

6. **実装時の品質保証（絶対遵守）**
   - リファクタリングを実装する場合、**必ず `read_lints` ツールでエラーを確認する**
   - エラーがある場合は **報告前に必ず修正する**
   - **Lintエラーが残っている状態での完了報告は禁止**

---

## 補足: なぜ複数回の提案で新たな候補が出続けるのか

以下の要因により、1回目の提案だけでは漏れが発生しやすい：

1. **スコープの段階的拡大**: 変更ファイル中心に分析すると、関連ファイルの「関連の連鎖」が途中で切れる
2. **類似パターンの後追い発見**: A を定数化したときに「B も同じベースだった」と気づくが、初回分析時は B を十分に見ていない
3. **クロスファイル検索の不足**: 同じ文字列・型・構造が他ファイルにあることを、体系的に検索していない
4. **分析の打ち切り**: 候補をいくつか見つけた時点で提案を確定し、他に同種のパターンがないか確認していない

上記を防ぐため、「重要な動作指示」4.1 のクロスファイルパターン検索と、Step 2 の網羅的関連ファイル特定を必須とする。

## 1. 基本方針

### 提案の優先順位

1. **小さくて簡単な方法から提案**
   - 変数名の改善
   - 定数の抽出
   - コードクローンの排除（同一・類似コードの共通化）
   - メソッド抽出（長大・複数責務の関数の分割）
   - 共通コンポーネントの作成（UI・ロジックの再利用）
   - 1つの関数の分割
   - 1つのファイルの分割

2. **ユーザー主導の対応**
   - Agent モードでも勝手に変更しない
   - 提案のみを行い、実装はユーザーに委ねる
   - 複数の選択肢を提示

3. **関連・類似ファイルの確認**
   - 「重要な動作指示」2. に従い、関連ファイルもリファクタリング対象に含める

4. **コード品質の優先順位**
   - **パフォーマンスよりも、可読性・保守性を優先する**
   - 著しくパフォーマンスに問題がある場合のみ、パフォーマンス改善を検討する
   - 意図の読み取りやすさ、デバッグしやすさ、将来の変更への対応を重視する
   - 提案が特にない場合は、無理に提案しない

5. **ファイル分割の方針**
   - **メインファイルの肥大化を避けることを優先する**（詳細は `coding-standards.md` の「ファイル分割の指針」を参照）
   - 再利用可能な機能や独立した責任を持つ機能の分割を積極的に提案する
   - ファイル分割により、メインファイルの可読性と保守性が向上する場合は分割を推奨する

6. **推奨するリファクタリング方針（必ず検討すること）**
   - リファクタリング提案時は、以下を**必ず分析し、該当する場合は提案に含める**。
   - **コードクローンの排除**: 同一・類似のコードが2箇所以上にある場合は、関数・モジュール・コンポーネントへの共通化を提案する。`coding-standards.md` の「コードの重複は撲滅」に従う。
   - **メソッド抽出**: 長大な関数や複数の責任を持つ関数は、意図の単位でメソッド・関数に抽出することを提案する。
   - **共通コンポーネントの作成**: 複数箇所で同じUI・同じ振る舞いが使われている場合は、共通コンポーネントや共通関数への抽出を提案する。類似コンポーネントの統合も検討する。

7. **提案しないパターン（絶対に提案しないこと）**
   - **`async () => await fn()` の簡素化**: Promise を返す関数を fetcher として渡す際の `async () => await fn()` を `() => fn()` に変更する提案は行わない。このパターンは提案対象外とする。

## 2. リファクタリング提案の手順

（対象の特定・除外条件・提案件数は「重要な動作指示」を参照）

**方針**: 1回の分析で可能な限りすべての候補を洗い出す。複数回のやり取りで「新たな提案」が続くことを避ける。

### Step 1: リファクタリング対象の分析

- ファイルや関数の行数・複雑度（閾値は `coding-standards.md` の「複雑度制限」を参照）
- ネストレベルやパラメータ数（閾値は `coding-standards.md` を参照）
- 複数の責任を持つファイルかどうか
- 密結合な部分の特定
- プロジェクト全体の場合は、最も問題のあるファイルを特定

### Step 2: 関連ファイルの網羅的特定

「重要な動作指示」2. を参照。**漏れのないよう**以下をすべて確認する：

- インポート関係（インポート元・インポート先の両方）
- 同じディレクトリ内の全ファイル
- 同じ機能領域の全ファイル（例: sticky-header なら constants, components, utils, hooks すべて）
- 類似名・類似責務のファイル

### Step 3: クロスファイルパターン検索（提案確定前に必須）

分析スコープ全体で以下を検索し、類似パターンを見逃さない：

- **文字列リテラル**: 同じ Tailwind クラス、数値、文言が他ファイルにないか（`grep` や意味検索で確認）
- **型の重複**: 同じユニオン型や interface が複数ファイルで定義されていないか
- **構造の類似**: 同じマークアップ・同じロジックパターンが他にないか
- **定数化の連鎖**: 1つ定数化したら、同じベースを使う別の箇所が他にないか

### Step 4: リファクタリング候補の特定

Step 1〜3 の結果を踏まえ、候補を特定する。提案件数のルールは「重要な動作指示」4. を参照。

#### 高優先度の候補

1. **メインファイルの分割**
   - メインファイルの肥大化を避けるため、再利用可能な機能や独立した責任を持つ機能の分割
   - メインファイルが主要な処理フローに集中できるように、詳細な実装を別ファイルに分離
   - 例: ユーザー入力処理、エラーハンドリング、ユーティリティ関数など

2. **関数の分割**
   - 行数・複雑度が `coding-standards.md` の基準を超える関数
   - 複数の責任を持つ関数

3. **ファイルの分割**
   - 300行を超えるファイル
   - 複数の責任を持つファイル
   - 関連性の低い機能が混在

4. **名前空間オブジェクトエクスポートの適用**
   - 個別の関数エクスポート（`export { func1, func2 }`）を名前空間オブジェクトエクスポートに変更
   - 詳細は `coding-standards.md` の「名前空間オブジェクトエクスポート（必須）」を参照
   - **ただし、定数のみのエクスポート（例: `constants.ts`）については、名前空間オブジェクト化は不要とする**

5. **型定義の改善**
   - `any` の使用
   - 型定義の不足
   - 型の安全性向上

#### 中優先度の候補

6. **定数の抽出**
   - `coding-standards.md` で定められたマジックナンバーや繰り返し値の定数化
   - ハードコードされた文字列の再利用整理

7. **変数名の改善**
   - `coding-standards.md` の命名規則に合致しない名前の見直し
   - 意味が不明確・長すぎる名前の再検討

8. **コードクローンの排除**
   - 同一・類似のコードが2箇所以上ある場合は、**必ず**共通化を提案する。関数・モジュール・ユーティリティへの抽出、または共通コンポーネント化を行う。
   - プロジェクト全体または関連ファイルを確認し、重複箇所を特定してから提案する。`coding-standards.md` の「コードの重複は撲滅」に従う。

9. **メソッド抽出**
   - 行数が多い関数、複数の責任を持つ関数は、処理の塊ごとにメソッド・関数へ抽出することを提案する。
   - 抽出後の関数名で意図が分かるようにし、`coding-standards.md` の「意図が不明瞭な処理は関数に抽出」に沿う。

10. **共通コンポーネントの作成**
    - 同じマークアップ・同じ振る舞いが複数箇所にある場合は、共通コンポーネント（Svelte コンポーネントや共通関数）への抽出を提案する。
    - 類似したコンポーネントが複数ある場合は、props で差を吸収する1つの共通コンポーネントへの統合を検討する。

#### 低優先度の候補

11. **コードの整理**
    - `coding-standards.md` で禁止されている未使用の変数・関数の削除
    - 重複コードや不要なコメントの削除（共通化後の残り屑の整理を含む）

## 3. 提案の形式

### 提案テンプレート

各提案は以下の構成で記述する：

- **優先度**: 高 / 中 / 低
- **現在の状況**: 問題点、現在のコードの状況
- **提案内容**: 具体的な改善案、期待される効果
- **実装方法**: ステップバイステップの手順、注意点
- **サンプルコード**: そのまま利用できる具体的なコード（`coding-standards.md` の規約に準拠、lintエラーがないことを確認済み）
- **関連ファイル**: 影響を受けるファイル、確認すべきファイル

### コード規約の遵守

サンプルコードは `prompts/coding-standards.md` の規約に従うこと。命名規則、名前空間オブジェクトエクスポート、関数構文など、詳細は同ドキュメントを参照。

---

## 4. ESLint ルールとの整合性

- 分割した関数・ファイル、提案するサンプルコード、新規作成するファイルがESLintルールに準拠しているか確認する
- 大きなリファクタリングでは一時的にルール違反が発生する可能性があるため、各段階でlintエラーをチェックして解決する
- 具体的なルールや閾値は `prompts/coding-standards.md` に集約されている。提案・サンプルコードの作成前に必ず確認すること。

## 5. 提案時の注意点

### ユーザーへの配慮

1. **選択肢の提示**
   - 複数の実装方法を提示
   - メリット・デメリットを説明
   - ユーザーが判断できる情報を提供

2. **段階的な提案**
   - 小さな変更から開始
   - 大きな変更は後回し
   - 各段階で効果を確認

3. **実装の委譲**
   - 「1. 基本方針」2. のユーザー主導の対応に従う

### 技術的な配慮

1. **既存コードの尊重**
   - 現在の設計思想を理解
   - 既存のパターンに従う
   - 破壊的変更を避ける

2. **テストの考慮**
   - 既存テストへの影響を確認
   - 新しいテストの必要性を検討
   - テストの可読性を向上

3. **パフォーマンスの考慮**
   - リファクタリングによる性能劣化を避ける
   - 不要な処理の追加を避ける
   - 既存の最適化を維持
   - 「1. 基本方針」4. のコード品質の優先順位に従う

4. **コード品質の評価基準**
   - **意図の読み取りやすさ**: コードを読んだだけで何をしているか理解できるか
   - **デバッグしやすさ**: 問題発生時に原因を特定しやすいか
   - **将来の変更への対応**: 要件変更や機能追加に対応しやすいか
   - これらの観点から、現状のコードが適切な場合は無理に提案しない

## 7. チェックリスト

提案前に以下を確認：

- [ ] **関連ファイルを網羅的に特定した**（インポート元・先、同ディレクトリ、同機能領域、類似名）
- [ ] **クロスファイルパターン検索を実施した**（同一・類似の文字列、型、構造を他ファイルで確認）
- [ ] **1回の提案で洗い出し切れたか確認した**（「似たパターンが他にもある」と後から気づく漏れがないか）
- [ ] **提案するサンプルコードにlintエラーがないことを確認した**
- [ ] **新規作成するファイルのコードにlintエラーがないことを確認した**
- [ ] **サンプルコードが `coding-standards.md` の規約に準拠しているか確認した**（名前空間オブジェクト、関数構文など）
- [ ] 現在のファイルの状況を正確に把握した
- [ ] 提案件数のルールに従っている（高・中優先度は制限なし、すべて低優先度の場合のみ最大3つ）
- [ ] 実装可能なサンプルコードを提供している
- [ ] 実装はユーザーに委ねている（「1. 基本方針」2. 参照）
- [ ] 既存の設計思想を尊重している
- [ ] テストへの影響を考慮している
- [ ] パフォーマンスへの影響を考慮している

## 9. リファクタリング実装後の報告手順

**重要**: ユーザーが「対応して」などと指示してリファクタリングを実装した場合、**例外なく以下の手順を実行してください**：

1. **実装後のlintエラーチェック（絶対必須）**
   - リファクタリング実装直後に、**必ず `read_lints` ツールを実行する**
   - `read_lints({ paths: ['変更したファイル1', '変更したファイル2', '新規作成したファイル1'] })` のように、**すべての関与したファイルを指定して確認する**
   - この手順を省略することは禁止されています

2. **lintエラーの即時修正（修正ループ）**
   - lintエラーが1つでも見つかった場合、**ユーザーに報告する前に修正を行う**
   - 修正後、再度 `read_lints` を実行し、エラーが0件になるまで繰り返す
   - **Lintエラーが残っている状態での完了報告は禁止**

3. **報告内容**
   - 実施した変更内容を説明
   - **「Lintエラーチェックを実施し、エラーがないことを確認しました」** と明記する
   - もし自動修正できないエラーが残った場合のみ、その理由と共に報告する

4. **`coding-standards.md` の Lint 手順に従う**
   - `read_lints` に加え、**必ず `pnpm run lint` で検証する**（`read_lints` は一部のルールを検出しないため）

**重要**: 「リファクタリングを提案して」と指示された場合、「重要な動作指示」1〜4 を実行する。
