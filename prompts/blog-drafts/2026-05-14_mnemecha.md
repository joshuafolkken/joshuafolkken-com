#### E-5. ポインタロックを捨てて右ドラッグカメラに変えた話 [mnemecha#101, #103]

PC 操作の大転換：

- 最初は標準的な FPS の **PointerLock**（カーソル消える、画面中央 raycast）
- 問題：カーソルが消えるので 3D オブジェクトを直接クリックできない。Raycast が画面中央固定。
- 結論：**Roblox 風に右ドラッグでカメラ回転、左クリックでオブジェクトクリック**。トラックパッドの 2 本指 pan でもカメラ操作可。

**「常識だった PointerLock を捨てた」という pivot 話**。

#### E-6. モバイル操作の闇深い話 3 連発 [mnemecha#90, #91, #131]

A-2 既存ネタの「モバイル操作を何度も調整」の中身：

- **#90 invisible joystick zones**：可視ジョイスティック UI を撤去 → 左半分=移動・右半分=カメラの不可視ゾーン。2 本指タッチを touch identifier で独立追跡。Threlte に **synthetic PointerEvent** を `offsetX/Y` 明示で投げて `calculateDistance` チェックを通すハック。
- **#91 iOS Safari 用 CSS 疑似フルスクリーン**：iPhone Safari は標準 Fullscreen API 不可 → `position: fixed; inset: 0; z-index: 9999` でフォールバック。
- **#131 touchcancel バグ**：電話着信などで `touchcancel` 発火 → `pointerup` が Threlte に飛ばず **ドラッグ状態が固まる**。回帰テスト付きで修正。

**「モバイル Web で 3D ゲームを真面目に作ると遭遇する罠カタログ」**として 1 セクション組める。

#### E-7. モバイル GPU 最適化の 5 軸 [mnemecha#113]

A-1（CYBER scene 犯人探し #198）と組み合わせ可能な、より広いパフォーマンス最適化の話：

1. **DPR 制限**：`<Canvas dpr={[1, 2]}>`。iPhone は native DPR=3 → 9 倍のピクセル数だった。
2. **モバイルで shadow OFF**：PointLight ごとに 6 枚の shadow map レンダリングが走る。
3. **antialias 設定明示**：モバイル GPU のデフォルト MSAA を回避。
4. **shader precision を `mediump` へ**：デフォルト `highp` は不要。
5. **emissive intensity 削減**：bloom なしで 3.0 / 5.0 は GPU 無駄。

→ **「FPS 30 → 60 への道は 5 + 1 軸の最適化」**みたいな構成で書けば、ゲーム × WebGL の読者層に強く刺さる。

#### E-8. Cyber モードが暗すぎ問題 [mnemecha#26]

#### E-9. Cloudflare Workers ならではの罠：`PUBLIC_APP_VERSION` injection [mnemecha#135]

#### E-10. FSM タイマーリーク + AudioContext suspend [mnemecha#125]

Mnemecha の FSM（finite state machine）にタイマーがリークしてた / Web Audio の AudioContext が suspend されてた問題。**「ゲーム開発 = 状態管理地獄」**枠として短く触れられる。

## 文中で触れたいスコア式と判定タイミングの公式

### スコア式（per-round time coefficient） [mnemecha#142]

```text
round_score          = 1,000 × time_coefficient × round_number
time_coefficient     = max(0.1, 1.0 − avg_seconds_per_button × 0.1)
avg_seconds_per_button = elapsed_seconds ÷ sequence_length
```

例：

- Round 5 を 8 秒でクリア → avg=1.6 s/button → 係数=0.84 → **4,200 pt**
- Round 10 を 20 秒でクリア → avg=2.0 s/button → 係数=0.80 → **8,000 pt**

「**シーケンスが長くなれば 1 ボタンあたりの平均時間も上がりやすい**」のを `avg_seconds_per_button` で正規化して **長いラウンドでも公平にスピードボーナス**を出すのが工夫ポイント。
